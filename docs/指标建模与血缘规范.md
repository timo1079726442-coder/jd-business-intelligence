# 指标建模与血缘规范

## 1. 目标与分层

生产链路统一为：

```text
Collector → Raw → Standard → Derived / Enriched → Metric → Service → API → Dashboard → AI Tool
```

- **Raw**：京东接口或下载报表实际返回的字段，只保存原始值，不放业务推导。
- **Standard**：统一字段名、类型、店铺、业务日期、SKU/SPU及唯一键；必须保留来源字段和来源批次。
- **Derived / Enriched**：复现可审计的业务派生规则，例如订单级退款汇总、金额拆分、订单计数标记、出库状态归一。
- **Metric**：面向经营问题的聚合指标。
- **Composite Metric**：只依赖已登记的 Metric，不重复实现底层字段逻辑。
- **Service**：统一为 Dashboard、API 和未来 AI Agent 提供业务查询能力。

## 2. Metric 登记规范

每个指标登记一条记录，至少包含：

| 字段 | 要求 |
|---|---|
| metric_key / metric_name | 稳定英文键和中文名称 |
| business_question | 该指标回答的业务问题 |
| definition | 业务定义，包含统计对象与边界 |
| formula | 可读公式或规则说明；不得只写代码片段 |
| dependencies | 依赖的 Metric/Derived Field 键，形成 DAG |
| source_fields | 直接使用的 Standard 字段 |
| derived_fields | 依赖的 Derived 字段 |
| filters | 状态、渠道、店铺等过滤条件 |
| grain | 行、订单、商品、店铺或日期粒度 |
| time_semantics | 下单日、付款日、退款发生日等 |
| shop_semantics | 店铺筛选和多店隔离规则 |
| aggregation | SUM、COUNT、COUNT DISTINCT、比率等 |
| null_policy | 空值、零值和缺失数据处理 |
| version / status | 口径版本和 draft/active/deprecated 状态 |
| validation_rule | 对账、范围、数量或回归校验 |

示例依赖关系：

```text
estimated_profit
└── net_gmv
    ├── gmv
    └── refund_amount
```

利润公式不得再次复制成交金额和退款金额的底层实现。

## 3. Derived Field 登记规范

每个派生字段至少包含：

| 字段 | 要求 |
|---|---|
| field_key / field_name | 稳定键和业务名称 |
| definition | 字段含义和适用范围 |
| formula_or_rule | SQL/Python 可实现的规则 |
| dependencies | 依赖的 Derived/Standard 字段 |
| source_fields | 直接来源字段 |
| grain | 明细、订单、商品或店铺粒度 |
| partition_key | 分组键，例如 shop_pin + order_id |
| ordering_dependency | 是否依赖稳定排序或首次出现 |
| time_semantics | 派生使用的时间口径 |
| version / status | 版本和生命周期状态 |
| validation_rule | 与旧 Excel/API 的验证方式 |

旧 Excel 公式只作为 `Legacy Business Rule Migration` 来源。公式解析结果必须转写成业务规则，不能让生产系统继续依赖 Excel 执行。

## 4. 指标新增流程

1. 先说明业务问题和统计对象。
2. 搜索已有 Metric、Derived Field、Standard 和 Raw 字段。
3. 明确粒度、时间口径、店铺口径、空值策略和聚合方式。
4. 如存在多个合理定义，列出候选口径及业务差异，等待确认，不自行选择。
5. 建立完整血缘和 DAG，登记新版本。
6. 实现 Derived/Metric、Service、API 与最小必要 Dashboard。
7. 增加单元测试、边界测试、对账测试和数据质量检查。
8. 验证通过后将状态从 draft 改为 active。

## 5. 版本与变更

- 口径变化必须递增 `metric_version` 或 `field_version`，禁止静默覆盖旧口径。
- API 响应必须返回 `metric_version`、`generated_at`、`data_updated_at`。
- 历史规则迁移时保留生效区间；无法证明来源的历史常量标记为 `UNRESOLVED`。
- Raw 和 Standard 不因新指标增加假字段；派生结果进入 Derived 层。
- 任何生产重算前必须生成预览、对账报告和可回滚记录。

## 6. 验证与数据质量

每个 active 指标至少验证：

- 字段存在性、类型和唯一键。
- 日期范围、店铺隔离和粒度不重复。
- 分子、分母及零除处理。
- 与原始报表或旧 Excel 的抽样对账。
- 缺失、空表、鉴权失败和部分数据场景。
- 结果可追溯到 Raw 批次、规则版本和查询时间。

## 7. 对外服务边界

Dashboard 与未来 AI Agent 只能调用稳定 Service，例如：

`get_shop_overview`、`get_shop_comparison`、`get_product_analysis`、`get_promotion_analysis`、`get_refund_analysis`、`get_data_quality`。

Service 负责执行已登记的 Metric，调用方不得直接读取 `raw_biz_*` 或自行复制公式。

## 8. 当前 MIYO 迁移边界

BZ、CA、CB、CC、CD、售后 AX、售后 AY 属于待迁移 Derived/Enriched 字段；订单列表 A/G/I/L/M/AC、售后 K/AJ/H/M 是当前递归链中的终端输入候选。Standard 映射仍须以当前 API/下载字段核验，不能仅凭旧 Excel 列位推断。
