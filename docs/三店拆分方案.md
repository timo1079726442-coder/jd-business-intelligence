# 三店拆分方案（2026-08-21 设计稿，待用户确认后实施）

## 一、目标

- 当前 main.py 10,119 行单文件 → 拆为 4 个文件
- 影刀可以分别按业务域调用 Python 模块：`python run_sz.py --shop FYA`、`python run_jzt.py --shop FYA`
- 业务逻辑不重复，调度入口不重复

## 三、影刀调用方式

| 场景 | 影刀执行命令 | 说明 |
|------|--------------|------|
| 跑单个商智业务 | `python run_sz.py --shop FYA --biz 商品流量来源_搜索 --date 2026-08-20` | 影刀脚本轻 |
| 跑商智所有业务 | `python run_sz.py --shop FYA` | 内部遍历 7 个 SZ 业务 |
| 跑京麦全量 | `python run_jm.py --shop FYA` | 包括 IMAP 密码等待 |
| 跑京准通全量 | `python run_jzt.py --shop FYA` | 100 上限防护生效 |
| **全量 3 店串行** | `python rpa_run.py` | 保留原行为，店间 60s 冷却 |

## 四、拆分原则

1. **基类不拆**：`JDBaseRequest`（Cookie/重试/UA/Excel）保留在 main.py，作为公共基类
2. **业务类 1:1 拆分**：每个 `XXXAPI` 类独立到一个文件
3. **注册中心保留**：`BUSINESS_REGISTRY` 仍在 main.py，新业务在 modules 子包里定义后导入注册
4. **零行为变更**：拆分后所有 rpa_run.py 用法、config.xlsx 配置、auth 文件保持不变
5. **保留 main.py 兼容**：旧 `python main.py --biz_key xxx` 仍可工作（代理到 modules）

## 六、风险与缓解

| 风险 | 缓解措施 |
|------|----------|
| import 循环依赖 | 基类放 main.py，业务子类放 modules；注册中心 import 时机延后 |
| 旧 `main.py --biz_key xxx` 失效 | 保留兼容入口，代理到 modules |
| 100 上限防护类位置不变 | 已在 main.py，模块化不影响 |
| 测试用例找不到类 | `tests/test_*.py` 改 import 路径：`from modules.jzt.kuaiche import JZTKuaicheAPI` |

## 七、不拆 main.py 的备选方案

如果用户觉得拆模块太重，可只做"轻拆"：
- main.py 保留，但加 `run_sz.py` / `run_jzt.py` / `run_jm.py` 三个**纯转发**脚本（只接受参数，调 main.py 对应函数）
- 不动内部结构，2 小时内完成
- 影刀就能按业务域独立调用
