# 阶段1B统一数据流水线实施报告

实施日期：2026-08-30

## 1. 新入口与流程

唯一推荐入口为 `run_pipeline.py`。它按以下链路运行：

```text
Cookie / h5st（影刀未来仅负责保存）
  → 配置读取与店铺解析
  → Data Plan
  → 鉴权文件预检
  → 既有业务 Collector
  → Excel 归档 + SQLite Upsert
  → MySQL Standard 增量同步
  → Derived View 健康检查
  → Metric Service smoke test
  → 数据质量检查 + JSON Summary + 退出码
```

本阶段未修改影刀流程，也没有删除、DROP 或 TRUNCATE 任一历史业务表。

## 2. Run / Task 批次追踪

新增独立 SQLite 元数据表：

- `etl_run`：`run_id`、开始/结束时间、触发来源（`manual`/`rpa`/`scheduled`）、状态、主机、Python/应用/配置版本、店铺清单、错误摘要。
- `etl_task_run`：`task_id`、`run_id`、店铺 Key/Pin、业务、请求起止日期、粒度、任务类型、状态、行数、错误、来源请求 ID。

历史业务表没有被增加 `batch_id`；历史数据因此保持 `LEGACY_UNTRACKED` 语义，不伪造批次。

## 3. 任务状态与补数策略

成功：`SUCCESS_WITH_DATA`、`SUCCESS_EMPTY`。后者表示平台真实空表，不写伪造的零值记录。

失败：`FAILED_AUTH`、`FAILED_REQUEST`、`FAILED_PARSE`、`FAILED_DATABASE`、`FAILED_VALIDATION`。

策略由现有 `config.xlsx` 和既有 `run_daily.py` 规则生成：

- 京麦订单/售后：`ROLLING_REFRESH`，最近 30 天覆盖更新，30 天以前不触碰。
- 支持区间的业务：连续缺失日期合并为一个区间任务，例如 8/24–8/26。
- 仅支持单日的业务：每个缺失日期一个任务。
- 月度业务：按自然月生成任务，绝不退化成逐日请求。

## 4. SQLite、MySQL、Derived 与 Metric

- SQLite 沿用现有按 `shop_pin + stat_date` 覆盖 Upsert，重复运行不应累加。
- 新 MySQL 同步仅删除并重插“本任务店铺 + 业务 + 日期范围”；不调用旧 `build_mysql_standard_tables.py`，该脚本含全表 `DROP`。
- `vw_derived_jm_order_full` 只做可读健康检查，不在每次 Run 重建。
- 最后调用 `MetricService.get_shop_overview()` 作为不依赖浏览器的 smoke test。

## 5. dry-run、过滤与退出码

示例：

```powershell
python run_pipeline.py --shop MIYO --dry-run
python run_pipeline.py --shop MIYO --biz "京麦订单明细_完整一键导出"
python run_pipeline.py --shop MIYO --start 2026-08-24 --end 2026-08-26
```

`--dry-run` 读取配置、SQLite 缺口和鉴权文件状态，但不会请求京东 API、写 SQLite 或写 MySQL。

固定退出码：`0` 全成功；`10` 部分失败；`20` 鉴权；`30` 请求；`40` 解析；`50` 数据库；`60` 数据质量；`70` 参数错误。

stdout 最后一行固定输出 JSON Summary；完整结果文件为 `runtime/runs/<run_id>.json`，日志为 `logs/jd_pipeline_YYYYMMDD.log`。两者均不记录 Cookie、h5st、密码或 token。

## 6. 数据质量检查

仅检查本次成功任务范围，避免全库扫描：任务失败、源表/公共字段缺失、空店铺标识、精确重复候选、最新数据日期、MySQL 同步、Derived View 和 Metric Service。

超过 50,000 行的大任务跳过全行哈希重复检查并在 Summary 标注 `SKIPPED_LARGE_TASK`；这是防止大报表拖慢日常流水线的明确降级，而不是把它误报为“无重复”。
