## 一、需求背景

旧的报表落盘模式是按"店铺/业务/日期"拆出几十上百个 xlsx：
```
output/
  FYA箱包旗舰店/
    京麦订单明细/
      2026-08-10/订单明细_2026-08-10.xlsx
      2026-08-15/订单明细_2026-08-15.xlsx
      ...
    搜索流量/
      2026-08-13/搜索流量_2026-08-13.xlsx
      ...
```

**问题**：
- 文件碎片化，30 天 × 20 业务 × 3 店 = 1800 个文件，查找不便
- 跨日跨业务汇总要靠外部工具（pandas/SQL）
- 单日落盘模式 + 单日 DB 入库，无法保证 Excel 和 DB 一致性

**新方案**：
```
output/
  总表/
    FYA8888_商智总表.xlsx     # 7 sheets
    FYA8888_京准通总表.xlsx   # 6 sheets
    FYA8888_京麦总表.xlsx     # 2 sheets
    miyo-周_商智总表.xlsx
    miyo-周_京准通总表.xlsx
    miyo-周_京麦总表.xlsx
    ota8888_商智总表.xlsx
    ota8888_京准通总表.xlsx
    ota8888_京麦总表.xlsx
```

每张总表每个 sheet 纵向存储所有历史数据（一行一条明细 + `stat_date` 列），
旧数据通过 90 万阈值自动清理。MySQL/SQLite 仍然是真相源。

## 三、核心架构

### 3.1 数据流

```
业务类 (main.py)
  └─ save_to_db(biz_key, df, report_date)         # DB 入库
       ├─ upsert_df() → SQLite (biz_xxx 表)       # 真相源
       └─ excel_master.collect(biz_key, df, date)  # 暂存到 _CACHE
                                                  # ↓ (main() 出口/调度脚本收尾)
main.py main() 出口 / daily_update.py / fill_missing.py / refresh_reports.py
  └─ excel_master.flush_shop(shop_id, shop_pin)
       ├─ _take_cache_for_shop() → 取出数据
       ├─ _flush_one_file(sz) → 商智总表
       ├─ _flush_one_file(jzt) → 京准通总表
       └─ _flush_one_file(jm) → 京麦总表
            └─ load_workbook → delete 受影响 stat_date 行
                              → append 新数据
                              → 90万阈值清理（可选）
                              → 冻结首列/表头
                              → save
```

### 3.2 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 触发时机 | `main.py run()` 出口 + 调度脚本尾部 | 所有 MySQL/SQLite 写入完成后再统一刷，符合用户 spec |
| 业务 ↔ sheet 映射 | config.xlsx「Excel总表映射」sheet | 符合 AGENTS.md 第3条（业务参数走 config） |
| 增量更新方式 | `load_workbook` + delete + append | 保留样式/合并单元格/冻结窗格；不重建文件 |
| 受影响日期处理 | delete rows where `stat_date IN affected_dates` | 同一日期多次跑全量数据都能正确覆盖 |
| 90 万阈值 | 删除最早 60 天（按 stat_date 升序第 60 个日期） | 用户决策；保留 90 万最新数据 |
| 空数据保护 | df 为空时跳过该 sheet，不动现有数据 | 用户决策；空报表不污染历史 |
| 跨店隔离 | 按 `shop_pin` 在 `_CACHE` 内分组 | 多店并发安全 |
| 业务类侵入度 | **零侵入** | `save_to_db` 内自动联动，业务类不需要改任何代码 |
| 旧的单日 xlsx 落盘 | **保留**（用户决策 2026-08-22） | 作为数据备份；不删除历史文件 |

### 3.3 90 万阈值性能优化

触发清理时（>= 90 万行），如果用 openpyxl 的 `ws.delete_rows(idx, 1)` 逐行删除，
会触发 60 万次内部 cell map 重建 → **预计卡死 30+ 分钟**。

**优化方案**（`excel_master.py:_check_threshold_and_cleanup`）：
```python
# 1. 用 ws.values 一次性读全部数据成 DataFrame（保留表头）
data = list(ws.values)
df_all = pd.DataFrame(data[1:], columns=data[0])

# 2. 解析 stat_date 成 datetime（pd.to_datetime 自动处理 str/int/datetime）
df_all['stat_date'] = pd.to_datetime(df_all['stat_date'], errors='coerce')

# 3. 按"日期"计数（不是按行！）取 cutoff
unique_dates = sorted(df_all['stat_date'].unique())
cutoff_dt = unique_dates[CLEANUP_DAYS - 1]  # 第 60 个不同日期

# 4. 过滤 cutoff 之后的行
df_kept = df_all[df_all['stat_date'] > cutoff_dt]

# 5. 整 sheet 重写（避免 O(N) 次 delete_rows）
del wb[sheet_name]
new_ws = wb.create_sheet(sheet_name, index=sheet_idx)
new_ws.append(headers)
for row in df_kept.itertuples(index=False):
    new_ws.append([v if pd.notna(v) else "" for v in row])
```

**实测**：91 万行触发清理 + 31 万行保留，耗时约 2-3 分钟（比 60 万次 delete_rows 快 10 倍+）。

> ⚠️ **已知性能限制**：91 万行 → 31 万行的清理需要 append 31 万次（约 2-3 分钟），
> 但触发频率极低（业务 4.5 年才可能触发一次）。如果未来需要频繁触发，
> 可改用 `pandas.DataFrame.to_excel(writer)` 一次性写。

## 四、关键代码片段

### 4.1 `excel_master.collect()` — 业务类调用入口

```python
def collect(biz_key: str, df, report_date: str, granularity: Optional[str] = None) -> None:
    """业务类调用入口：把 df 暂存到对应店铺的缓存。"""
    with _CACHE_LOCK:
        shop_pin = os.getenv("SHOP_PIN", "").strip()
        if not shop_pin:
            return

        if df is None or (hasattr(df, "empty") and df.empty):
            return  # 空数据跳过

        # 校验映射（biz_key 是否注册）
        mappings = _load_mapping_from_xlsx()
        mapping = next((m for m in mappings if m["biz_key"] == biz_key), None)
        if not mapping:
            logging.warning(f"biz_key 未注册：{biz_key}")
            return

        # 加 stat_date 列
        df_to_store = df.copy()
        if mapping["stat_date_alias"] not in df_to_store.columns:
            df_to_store[mapping["stat_date_alias"]] = report_date

        # 入缓存
        _CACHE.setdefault(shop_pin, {}).setdefault(biz_key, []).append({
            "df": df_to_store,
            "report_date": report_date,
            "granularity": granularity,
            "mapping": mapping,
        })
```

### 4.2 `flush_shop()` — 写一次所有 3 个总表

```python
def flush_shop(shop_id: str, shop_pin: str) -> dict:
    biz_to_records = _take_cache_for_shop(shop_pin)
    if not biz_to_records:
        return {}

    mappings = _load_mapping_from_xlsx()
    overall = {}
    for file_type in ("sz", "jzt", "jm"):
        if not any(m["file_type"] == file_type and m["biz_key"] in biz_to_records
                   for m in mappings):
            continue
        overall[file_type] = _flush_one_file(shop_pin, file_type, biz_to_records, mappings)
    return overall
```

### 4.3 单 sheet 写入逻辑（核心覆盖逻辑）

```python
# 1. 加载现有 sheet
wb = openpyxl.load_workbook(file_path) if os.path.exists(file_path) else openpyxl.Workbook()
ws = wb[sheet_name] if sheet_name in wb.sheetnames else wb.create_sheet(sheet_name)

# 2. 找 stat_date 列索引
header_cells = [c.value for c in ws[1]]
stat_date_col_idx = header_cells.index("stat_date") + 1
date_col_letter = openpyxl.utils.get_column_letter(stat_date_col_idx)

# 3. 删除受影响的 stat_date 行（从大到小避免索引错位）
rows_to_delete = []
for row_idx in range(2, ws.max_row + 1):
    val = ws[f"{date_col_letter}{row_idx}"].value
    if val and str(val).strip() in affected_dates:
        rows_to_delete.append(row_idx)
for row_idx in sorted(rows_to_delete, reverse=True):
    ws.delete_rows(row_idx, 1)

# 4. append 新数据
df_to_write["stat_date"] = pd.to_datetime(df_to_write["stat_date"]).dt.strftime("%Y-%m-%d")
for _, row in df_to_write.iterrows():
    ws.append([row[c] if pd.notna(row[c]) else "" for c in cols_in_order])

# 5. 90 万阈值清理（如触发）
_check_threshold_and_cleanup(ws, sheet_name)

# 6. 冻结首列 + 表头
ws.freeze_panes = "B2"
```

```python
# db_utils.py:save_to_db 末尾
if n > 0 and _excel_collect_hook is not None:
```

### 4.5 `main.py` 出口 hook

```python
# main.py:main() 末尾 + 异常路径都加
def _try_flush_excel_master_safe() -> None:
    """main() 出口的安全 flush：失败仅警告不抛错。"""
    try:
        import excel_master as _em
        from runtime_config import get_shop_id, get_shop_pin
        _em.flush_shop(get_shop_id(), get_shop_pin())
    except Exception as e:
        print(f"⚠️ [ExcelMaster] flush_shop 失败（不影响 DB 数据）：{e}")

# main() 出口 + 异常路径都调一次
try:
    results = run_business(biz_keys, **kwargs)
except CookieExpiredError:
    _try_flush_excel_master_safe()  # 鉴权过期也尝试刷（已 collect 部分还能写）
    sys.exit(1)
except Exception:
    _try_flush_excel_master_safe()  # 业务失败也尝试刷（前面成功部分已 collect）
    sys.exit(3)

# 全部成功路径
_try_flush_excel_master_safe()
```

## 七、退出码 & 异常处理

| 异常类型 | flush 行为 | 是否中断流程 |
|----------|------------|--------------|
| flush_shop 成功 | 正常 | 否 |
| flush_shop 失败（如文件被锁） | warning 后继续 | 否（不影响主流程退出码） |
| collect 时 biz_key 未在「Excel总表映射」注册 | warning 跳过 | 否 |
| collect 时 df 为空 | debug 跳过 | 否 |
| 90 万阈值触发 | warning 后自动清理 | 否（清理耗时 2-3 分钟） |

**核心原则**：**Excel 总表只是 DB 的可视化快照**。任何与总表相关的失败都不应该阻塞 MySQL/SQLite 入库。

## 九、2026-08-22 晚场：真实数据验证 + 踩坑记录

> 场景：FYA 单店跑批（京准通 30 天 + 京麦 30 天 + 商智 7 天）后验证总表行数，发现总表未更新。

### 9.1 根因 1：旧表 UNIQUE 不含 shop_pin（多店冲突 + 存量无归属）

- `biz_offline_channel` / `biz_keyword_analysis` 由旧版 `ensure_table` 创建，UNIQUE 为 `(report_date, 主键列)` **不含 shop_pin**，且存量行 `shop_pin=''`（早期未设 SHOP_PIN 环境变量）。
- 后果：本次跑批插入 FYA8888 时 UNIQUE 冲突 → `save_to_db` 抛异常 → `excel_master.collect` 未执行 → 总表行数不增。
- 修复：**数据保留迁移**（读旧表全量 → DROP → 逐日 `save_to_db` 重建，自动归属 FYA8888）。重建后 UNIQUE 为 `(shop_pin, stat_date, 主键列)`，多店隔离正确。
- ⚠️ MIYO/OTA 如存在同款旧表，需同样迁移（方法：一次性脚本，逻辑见下）。

### 9.2 根因 2：run_recent_30d 直调 handler，绕过 _auto_save_db_from_xlsx

- `main.run_business()` 有收尾钩子 `_auto_save_db_from_xlsx`（业务返回 xlsx 路径 → 读文件 → `save_to_db` → collect → flush）。
- 跑批脚本 `run_recent_30d.py` 直接调 `handler(**kwargs)`，**绕过了该钩子** → 京准通/京麦的 xlsx 生成成功但没进 DB/总表。
- 修复：写一次性 feed 脚本从真实 xlsx → `excel_master.collect`（按日期列拆分，stat_date 精确到日）→ `flush_shop`。
- 教训：**任何新跑批脚本必须走 `main.run_business` 调度器或补调 `_auto_save_db_from_xlsx`，否则总表/DB 缺数据**。

### 9.3 根因 3：京麦订单 IMAP 配置误删

- `config/imap_config.ini` 被误删（不在 git）。IMAP 授权码登记在 `config.xlsx「全局配置」sheet` 的 IMAP 组（`auth_code_last4` 掩码 + 备注）。
- 修复：用户把完整授权码登记到 xlsx（key=`授权码`，16 位），据此重建 ini（`user=1079726442@qq.com`, host=imap.qq.com, port=993, subject_keyword=京东密码转发），并把 `auth_code_last4` 更新为 `jcga`。
- 流程验证：`fetch_password_from_imap(task_id)` 一次轮询命中 → 用密码 `extract_xlsx_from_zip` 本地解压已下载 zip，**无需重建任务/重发短信**。

### 9.4 根因 4：excel_master 大批量删除 O(N²) 灾难

- `_flush_one_file` 原逻辑逐行 `ws.delete_rows()`，46k 行删 23k 行实测 **6 分钟+**。
- 修复：删除行数 > 1000 时改为**一次性重写**（`list(ws.values)` → 过滤 → 清空数据区 → append），实测 **< 5 秒**。
- ⚠️ 与 `_check_threshold_and_cleanup` 的 pandas 重写思路一致，后续可统一。

### 9.5 根因 5：pandas read_excel header=None 的坑

- `pd.read_excel(p, header=None)` 的 `None` 表示"无表头 → 数字列名"，**不是**"默认表头"！默认是 `header=0`。
- 误用导致所有单文件拆分失效（列名变 `[0,1,2,...]`），整文件被单日 collect（stat_date=07-23），产生大量垃圾行。
- 教训：需要"可传可不传"的 header 时，`if header is None: df = pd.read_excel(p) else: df = pd.read_excel(p, header=header)`。
