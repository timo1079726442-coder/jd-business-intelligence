# 未来业务板块标准接入方案

## 目标

在不推翻现有 Python + SQLite + MySQL + 原生前端架构的前提下，把新增业务变成可注册、可采集、可标准化、可查询、可展示的固定流水线：

```text
业务注册 → Collector → Raw → Standard → Metric → Service → API → Dashboard → 未来 AI Tool
```

MIYO 只作为第一家验证店铺；所有注册、指标和服务都必须以 `shop_key` 为参数，不能写成 MIYO 专用逻辑。

## 三个注册概念

### 1. 业务注册表

回答“系统有哪些业务”。现阶段继续使用 `config/config.xlsx` 的「业务清单」，渐进增加以下列：

| 字段 | 用途 |
|---|---|
| biz_key | 稳定业务标识，不能随意改名 |
| biz_name | 中文展示名称 |
| source | jingmai / jzt / shangzhi / product 等数据源 |
| module | 采集器模块路径或注册 key |
| enabled | 是否参与调度 |
| supports_range | 是否支持区间请求 |
| granularity | day / month / range |
| collector_key | 对应 Collector 注册名 |

已有列保持兼容；新增列为空时沿用现有默认行为。

### 2. 数据源定义

回答“数据来自哪里以及如何落库”。建议在配置表或独立 JSON/YAML 中登记：

```text
date_field
shop_field
unique_key
raw_table
std_table
empty_result_policy
status_policy
```

其中 `unique_key` 必须明确声明，不能由调度器临时猜测。

### 3. 指标字典

回答“数据如何组成指标”。建议第一阶段使用版本化 JSON 或 MySQL 元数据表，字段至少包括：

```text
metric_key
metric_name
definition
formula
dependencies
source_tables
source_fields
time_semantics
shop_semantics
unit
aggregation
null_policy
metric_version
notes
```

`dependencies` 用于表达指标下钻关系，例如：

```text
estimated_profit
├── net_gmv
│   ├── gmv
│   └── refund_amount
├── ad_cost
└── cost_parameters
```

## 新增业务的标准流程

### 第 1 步：业务注册

在「业务清单」增加一行，声明：

- 业务 key 和名称
- 数据源
- Collector key
- 是否启用
- 是否支持区间
- 粒度
- 输出目录
- 日期字段
- 店铺字段
- 唯一键
- Raw/Standard 表名

### 第 2 步：新增或复用 Collector

建议目录逐步形成：

```text
collectors/
├── jingmai/
├── jzt/
└── shangzhi/
```

Collector 负责：

- 组装请求
- 发送请求
- 解析响应
- 区分有数据、空表、鉴权失败、请求失败和解析失败
- 返回统一采集结果

调度器只负责读取配置、生成日期计划、找到 Collector、执行并记录结果。

### 第 3 步：建立 Raw 表

Raw 表保留接口原始字段和原始值，至少包含：

```text
id
shop_key
shop_pin
stat_date
report_date
etl_time
source_request_id
raw_payload_hash
原始业务字段...
```

Raw 层不负责经营指标计算。

### 第 4 步：建立 Standard 表

Standard 表负责字段标准化，统一：

- 日期格式
- 店铺标识
- 金额类型
- 数值类型
- 空值处理
- SKU/SPU 字段
- 业务唯一键

必须建立唯一索引或幂等写入规则，支持补数更新而不是删除整个时间段重灌。

### 第 5 步：声明补数策略

业务注册中声明：

- rolling_30d：京麦订单/售后近 30 天滚动更新
- range：缺失日期合并为一个区间请求
- day：仅支持单日时逐日请求
- month：关键词等月度粒度业务

空表必须记录为 `SUCCESS_EMPTY`，不能伪造 0 值业务记录。

### 第 6 步：声明指标

新业务产生的指标登记到指标字典，明确：

- 来源表
- 来源字段
- 时间字段
- 店铺字段
- 汇总方式
- 空值策略
- 依赖指标
- 指标版本

### 第 7 步：暴露 Service

业务逻辑放入 Service/Metric 层，例如：

```text
get_shop_overview
get_shop_comparison
get_product_overview
get_promotion_overview
get_refund_analysis
get_keyword_analysis
get_data_quality
```

Service 同时服务 Dashboard、API 和未来 AI，不允许前端、AI 各自重算公式。

### 第 8 步：增加 API

API 只负责：

- 参数校验
- 调用 Service
- 返回稳定 Schema
- 返回指标版本、生成时间和数据更新时间

推荐统一响应结构：

```json
{
  "shop": {},
  "period": {},
  "comparison_period": {},
  "metrics": {},
  "data_quality": {},
  "meta": {
    "metric_version": "...",
    "generated_at": "...",
    "data_updated_at": "..."
  }
}
```

### 第 9 步：增加 Dashboard 模块

不再把所有页面持续堆进一个 HTML。后续可按模块拆分：

```text
dashboard/modules/shop
dashboard/modules/product
dashboard/modules/promotion
dashboard/modules/order
dashboard/modules/traffic
dashboard/modules/keyword
dashboard/modules/data_quality
dashboard/modules/ai
```

本阶段只需完成全店看板稳定化，其他模块先保留目录和注册约定。

### 第 10 步：未来注册 AI Tool

本阶段不接大模型。未来 AI 只能调用 Service 封装的业务工具，不能直接读取 `raw_biz_*`。

## 本阶段应该实现

1. 完成 MIYO 全店指标血缘分析。
2. 固定 `/api/summary` Schema 和指标版本字段。
3. 建立第一版指标字典。
4. 建立 MIYO Excel/MySQL/API/页面四方对账框架。
5. 修复 Dashboard 单实例启动和端口检测。
6. 把 `mysql-connector-python` 补充到依赖文件。
7. 明确数据质量状态和空表处理。
8. 验证 shop_key 隔离。
9. 在不重写采集器的前提下，定义 Collector 注册接口。

## 本阶段只预留

- FYA、OTA 复用 MIYO 相同 Service/API/指标架构。
- 商品、推广、订单、流量和关键词看板模块目录。
- AI Tool 注册协议。
- `dim_shop` 等稳定维度表的渐进建设。

## 本阶段不应该做

- 接入 OpenAI、Claude 或其他大模型。
- 开发 AI 聊天框和 Agent。
- 同时重构全部采集器。
- 推翻现有 SQLite/MySQL 架构。
- 删除历史 Excel、SQLite 或旧 View。
- 为了模块化进行大规模 UI 重写。
- 在指标未完成 Excel 对账前修改生产口径。

## 低风险演进原则

新增业务优先采用“注册 + 适配器 + 标准表 + 指标声明”的增量方式；只有在重复逻辑已经被验证后再抽象公共代码。所有 Schema、指标和数据状态变化都必须保留版本和验证脚本。
